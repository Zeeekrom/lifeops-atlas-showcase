# LifeOps Atlas

<p><a href="README.md">English</a> · <strong>简体中文</strong></p>

[![公开发布检查](https://github.com/Zeeekrom/lifeops-atlas-showcase/actions/workflows/validate.yml/badge.svg)](https://github.com/Zeeekrom/lifeops-atlas-showcase/actions/workflows/validate.yml)
![演示数据](https://img.shields.io/badge/demo%20data-synthetic-0f766e)

LifeOps Atlas 把一个人的日程、联系人、跟进事项、机会和研究资料存成一份可靠的记录，并说明每条信息从哪里来。使用者用它安排每天的事、跟进联系过的人、留意活动和机会，以及准备求职申请。

它用 AI 协助，但由程序把关。AI 负责研究公开来源、根据记录回答问题、起草求职文字；保存什么由程序决定：AI 的输出要先通过校验才会保存，聊天不能修改记录，每一条消息、每一份申请都由使用者自己发出。

这是一个个人使用的单用户系统，在本机运行一套实例。它不是产品，不是云服务，也不是给团队用的 CRM。

应用源码、真实记录、提示词和配置都在私有仓库里。本仓库是经过筛选的作品集展示版，只放文档、注明日期的结果、合成数据演示和合成数据截图，不公开任何个人数据。

## 项目概况

| | |
|---|---|
| 这是什么 | 个人运营系统：日程、跟进、人脉、研究和求职准备放在同一个数据库里；AI 只读取和起草，不做决定 |
| 给谁用 | 自己管理联系人、活动、机会和求职申请的一个人。这个公开版是给软件、数据和应用支持方向的评审者看的 |
| 要解决的问题 | 日历、表格和聊天窗口各记了一部分。没有一个能同时留下“发生了什么、依据在哪里、下一步做什么”，而 AI 根据它们写的摘要也没法核对 |
| AI | 每晚的研究运行，报告发现并列出读过的来源；根据记录给出只读回答；根据使用者自己的材料起草求职文字。从 2026 年 11 月 15 日起，聊天和求职文字改用官方 Codex CLI，以隔离的纯文字模式运行；研究和 Discord 发送仍在 OpenClaw 上，迁移还没做完 |
| 技术栈 | TypeScript、Node.js 24、Fastify 5、Zod、PostgreSQL 17、Docker Compose、原生 HTML/CSS/JavaScript 和手机 PWA |
| 证据 | 2026 年 11 月 15 日：360 项测试中 342 项通过、18 项条件跳过；受限 AI 的诱饵测试没有发生任何工具调用；一次真实聊天完整走通队列。2026 年 10 月 29 日：418 条历史记录完成对账，27 项隔离 PostgreSQL 检查全部通过 |
| 数据 | 真实记录只在私有实例里。本仓库只有合成数据截图、合成数据演示，以及一份格式固定、注明日期的计数文件 |
| 状态 | 本机一套实例，由使用者自己在用；影子对比从 2026 年 9 月 16 日开始。不是多用户产品，也没有部署到云上。[互动演示](https://lifeops.evanh.dev/zh/)（2026 年 11 月）用虚构数据回放求职流水线的真实运行 |

## 要解决的问题

自己管理一条求职或业务线，每天都要回答同样几个问题，而大多数工具只能回答其中一部分：

- 今天该做什么？我在等谁回复？
- 上次和这个人聊是什么时候？我答应过要做什么？
- 最新一次导入，是不是把我手动改过的内容又盖掉了？
- 今晚的研究完整吗？有没有来源读取失败？
- 哪句话是我说的，哪句是活动上演讲者说的，哪句来自新闻？
- AI 能不能根据我的记录回答问题，同时又没有权限改记录？

LifeOps Atlas 用同一个数据库回答这些问题，并把每条信息的来源存在旁边。

## 给谁用

LifeOps Atlas 服务于自己管理一条线的一个人：比如在找工作的人、在新城市建立人脉的人，或者独立工作的人。下表是它在每个环节回答的问题。

| 场景 | 要回答的问题 | Atlas 给出的内容 |
|---|---|---|
| 安排今天 | 今天该做什么？在等谁？ | 今日日程和未完成的 Action（跟进事项），每条按自己的等待规则计时 |
| 跟进一个人 | 上次聊是什么时候？下一步是什么？ | 每个跟进对应一条 Action 和一段对话，状态怎么变都还是同一条 |
| 留意机会 | 今晚有什么新的？实际读了哪些来源？ | 雷达报告：发现、去掉的重复项和每个来源的覆盖情况 |
| 准备申请 | 能不能改简历又不动原件？ | 根据使用者自己的材料起草一份单独的 Summary 副本；申请由本人提交 |
| 核对数据 | 哪些记录对不上？为什么？ | 身份复核队列，以及固定的“哪种依据优先”的顺序 |

实际运行的实例只服务于使用者本人。给小团队等更多人使用是一个可能的方向，还没有做，也没有测试过。

## 一条跟进从头到尾

下面是示意，不含任何真实联系人或消息。

```mermaid
flowchart LR
    E[真实发生的事] --> A[一条 Action 和一段对话]
    S[每小时刷新来源，不用 AI] --> A
    A --> J[保存的任务]
    J --> W[AI 执行器：研究或回答]
    W --> V[校验输出，连同依据一起保存]
    V --> O[使用者决定]
    O --> U[使用者修改同一条 Action]
    U --> A
```

1. **真实的事发生了。** 使用者记下自己发出的一封邮件，关联到一个人和一条 Action。
2. **设好复查点。** 邮件跟进默认等七个自然日。没回复的领英消息有单独的规则，不会自动倒计时、显示逾期。
3. **刷新来源。** 一个协调器每小时重新读取允许的来源并对账，不调用 AI 模型。
4. **AI 工作作为保存好的任务运行。** 调用模型之前，任务连同它需要的记录先保存下来。研究运行会记下读过哪些来源；回答只用交给它的那些记录。
5. **校验并保存结果。** 输出先校验，再连同依据一起保存。“报告已保存”和“通知已送达”分开记录。
6. **由使用者决定。** 聊天给出解释或草稿。使用者在管理表单里修改这条 Action，消息和申请都由本人发出。下一阶段继续用同一条 Action 和同一段对话。

## AI 智能体在什么位置

AI 层由一个研究流程和两个范围更窄的文字执行器组成。它们共用 Atlas 的记录和任务队列，各自的边界不同。

| 角色 | 做什么 | 结果由什么把关 |
|---|---|---|
| 研究智能体 | 每晚研究允许的公开来源，写出带发现和来源覆盖情况的雷达章节 | 保存的任务、规定的输出格式、身份匹配、有上限的重试和明确标出的缺口 |
| 回答执行器 | 解释交给它的记录、对话和文本片段 | 聊天只读，模型文字不能修改记录 |
| 求职文字执行器 | 根据使用者自己的材料改写简历 Summary、起草普通申请问题的答案 | 来源事实、长度检查、受保护的模板和单独的申请程序 |
| 来源读取器 | 刷新选定的本地文本和已连接的来源 | 只读的允许文件清单或批准过的连接器操作；连上了不等于读取成功 |
| 应用协调器 | 安排工作、领取任务、校验结果、保存状态 | 普通程序代码、数据库约束和带审计的管理表单 |

```mermaid
flowchart TD
    UI[浏览器、手机 PWA 和求职入口] --> API[Fastify 应用]
    API <--> DB[(PostgreSQL 记录)]
    Sources[只读来源和白名单文本] --> API
    API --> Queue[保存的任务及所需记录]
    Queue --> Text[Codex CLI：回答和求职文字]
    Queue --> Radar[OpenClaw：研究，迁移中]
    Queue --> Career[求职文档与表单预填程序]
    Text --> Check[输出和依据校验]
    Radar --> Check
    Career --> Check
    Check --> DB
    UI --> Edits[使用者校验过的修改]
    Edits --> DB
    DB --> Delivery[已保存的报告和送达状态]
    Delivery --> Notify[通用手机通知或 Discord]
```

**11 月 15 日只完成了一部分迁移。** 聊天和求职文字现在调用官方 Codex CLI，使用使用者已有的 ChatGPT 登录。每次调用都在一个新的临时文件夹里运行，文件和网络权限受限，命令工具、网页搜索、应用和插件都关闭。调用失败时不会改走付费 API 或 OpenClaw。雷达研究和 Discord 发送仍依赖 OpenClaw。

求职表单预填是一个单独的程序，不是由文字模型操控的浏览器。敏感问题和最终提交都由本人完成。把上下文交给 ChatGPT 是明确的复制粘贴，不会搜索使用者的 ChatGPT 历史。

## 设计原则

- **记忆放在数据库里，不放在提示词里。** 当前事实存在 PostgreSQL 里，有约束、有历史。提示词只管行为和输出格式。
- **导入的一行是证据，不是事实。** 使用者的修正单独保存，下一次导入不会把它盖掉。
- **AI 只读取和起草，不改记录。** 聊天只读，修改要走校验过的管理表单。
- **先保存任务，再调用模型。** 额度用完、登录失效、网络断开都是常态，调用失败后留下的是保存好的请求，不会丢。
- **缺的来源就标为缺。** 只覆盖了一部分就报告“部分覆盖”；连上的来源要等真正读到了才算读过。
- **不同种类的证据分开放。** 本人的经历、演讲者的说法、关于别人的报告、技术新闻，是不同的来源类型。新闻永远不会变成个人技能。
- **由本人发出。** 消息、申请和最终提交都是手动的。
- **通知不透露隐私。** 手机通知预览只有固定的通用文字。
- **领英只能手动。** 无论登录与否，任何自动化都不碰领英。

来源之间说法不一致时，按这个顺序取舍：使用者明确的确认或修正，然后是核实过的当前证据、已确认的记录、导入的来源行、提示词默认值，模型推断排最后。

## 从问题变成的规则

| 出过的问题 | 改成了什么 |
|---|---|
| 后来的导入可能把手动修正盖掉 | 来源版本和修正分开保存，每次导入都重放优先级更高的修正 |
| 重新打开同一条 Action，历史容易散到好几段对话里 | 每条 Action 不论状态怎么变，都只用一段对话 |
| 排队中的雷达任务看起来像在运行 | 排队、执行器领取、报告已保存、消息已送达分成不同状态，失败和重试都显示出来 |
| AI 生成的修改建议不是可靠的改记录方式 | 停用可执行的聊天卡片，改走校验过的管理表单 |
| 手机还没连上私有网络时，通知可能露出隐私内容 | 通知只有固定的通用文字，详情在 Atlas 里打开 |
| 服务商或程序版本可能突然不能用 | 保留已保存的请求，给失败分类；要不要换备用方案写在策略里，不自动切换 |

## 技术栈

- TypeScript、Node.js 24、Fastify 5 和 Zod 数据协议
- PostgreSQL 17：约束、来源指纹、文本分块和词项排序（没有单独的向量数据库）
- 原生 HTML、CSS 和 JavaScript；中英文界面；带 Web Push 的手机 PWA
- 官方 Codex CLI 处理文字；剩下的研究和发送链路用 OpenClaw
- 求职试点复用部分 Career Ops 模块、Chromium 自动化和 Python 文档处理
- Docker Compose、主机执行器、只监听本机回环地址的恢复控制器，以及可选的私有网络（Tailscale）
- 自动化测试、隔离 PostgreSQL 检查、公开数据校验和注明日期的验收记录

组件和数据流见[架构说明](docs/architecture.md)，取舍见[工程决策](docs/engineering-decisions.md)。

## 安全与数据边界

- 公开演示没有后台、没有凭据，也不调用 AI，连不到私有实例。
- Codex 调用逐次受限：新的临时文件夹、不能随意访问文件、命令不能联网，命令工具、网页搜索、应用、插件和记忆功能都关闭。这些设置减少了单次调用能做的事，但不是完整的安全评估，也没有测试过 CLI 今后的变化。
- 聊天不能修改记录、执行 Action 或发送消息。使用者的修改走管理表单和带审计的记录管理器，并检查身份和版本；导入只写来源证据，不会覆盖修正。
- 恢复控制器只监听本机回环地址，只执行固定的操作清单。
- 手机通知预览只有固定的通用文字，打开详情需要私有网络。
- 公开来源读取器不绕过登录、robots 规则或人机验证。整个项目对领英只允许手动操作。
- 系统为一个人设计，不支持多用户访问，也不是多租户。

## 项目的收获

- 一份能修正的记录，比一段没法核对的摘要更有用。
- 先保存任务再调用模型，AI 失败时留下的是排队中的请求，而不是丢失的工作。
- 报告里写明哪些来源失败了，一份看起来很有把握的报告才算诚实。
- 让 AI 不碰写入路径，换服务商就是安全的：迁到 Codex 只换了一个执行器，记录没有受影响。
- 把“我做过的”和“我读到的”分开，新闻就不会变成简历上的能力。
