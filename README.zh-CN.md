## 问题与使用对象

日历保存一个约定，表格保存一个联系人，聊天生成一段有用的回答。
但这些东西分开时，很难保留“发生了什么、依据在哪里、下一步是什么”。

LifeOps Atlas 用持久记录把它们连起来。跟进事项改提醒、改状态后仍是同一条记录；
人工修正不会被下一轮导入盖掉；研究报告会说明实际读过哪些来源，还有哪些缺口。

实际运行实例服务于项目所有者。公开版让软件、数据和应用支持方面的评审者检查设计。
更广泛的小团队使用是后续方向，尚未经过用户部署验证。

## 一条跟进从头到尾

下面是示意流程，不含真实联系人的信息或消息。

```mermaid
flowchart LR
    E["已确认的互动事实"] --> A["同一条 Action 与对话"]
    A --> Q["保存任务与限定上下文"]
    Q --> R["研究或回答执行器"]
    R --> V["校验结果并保留依据"]
    V --> H["用户审核结果"]
    H --> U["更新原来的 Action"]
    U --> A
```

1. **先记录真实起点。** 用户记录一封已经发出的邮件，关联人物和 Action。
2. **按类别设置复查点。** 邮件跟进可使用配置中的七个自然日规则；
   等待对方回复领英消息采用独立规则，不自动生成逾期倒计时。
3. **刷新输入。** 一个每小时运行的协调器读取允许的来源并对账，普通同步不调用 AI。
4. **交给对应执行器。** 已保存的任务带入限定快照。研究记录来源覆盖情况，
   对话回答使用系统提供的 Atlas 依据。
5. **留下可以检查的结果。** 校验并保存回答或报告、来源以及实际返回的执行统计。
   报告保存和通知送达是不同状态。
6. **由用户决定下一步。** 聊天给出解释或草稿，用户通过管理页面更新原来的 Action，
   自己发送消息或提交申请。后续阶段继续复用这条记录和对话。

## AI 智能体在什么位置

AI 层包含一个研究智能体流程，以及范围更窄的回答和文案执行器。
它们共用 Atlas 状态和任务队列，各自的执行边界不同。

| 角色 | 实际负责什么 | 结果由什么约束 |
| --- | --- | --- |
| 研究智能体 | 从允许的公开来源研究新信号，生成含发现和来源覆盖的雷达章节 | 持久任务、输出协议、身份对账、有上限重试和明确的来源缺口 |
| 回答执行器 | 解释传入的 Atlas 快照、对话记录和检索片段 | 聊天只读，模型文字不能执行记录修改 |
| 求职文案执行器 | 根据提供的材料改写简历 Summary，草拟普通申请字段答案 | 来源事实、长度检查、受保护模板和独立的申请程序 |
| 证据读取器 | 刷新选定的本地文本和已连接来源 | 只读清单或批准的连接器操作；连上不等于本轮成功读取 |
| 应用协调器 | 调度、领取任务、校验和保存结果 | 确定性程序、数据库约束和带审计的管理页面 |

**11 月 15 日完成的是部分迁移。** 聊天和求职文字已改用官方 Codex CLI，
使用所有者的 ChatGPT 订阅。这些调用采用独立临时工作区和受限文件／网络权限，
关闭命令工具、网页搜索、应用和插件，不会失败后偷偷改走付费 API 或 OpenClaw。
雷达推理、Discord 发送和历史读取仍依赖 OpenClaw。

求职网页预填由独立程序执行，文案模型不控制浏览器。敏感问题和最终提交保留给用户。
ChatGPT 交接是明确的复制粘贴流程，不会搜索用户全部 ChatGPT 历史。

## 从问题变成的规则

| 实际遇到的问题或摩擦 | 形成的设计 |
| --- | --- |
| 后续导入可能覆盖人工修正 | 来源版本与明确修正分开保存，对账时重放优先级更高的修正 |
| 再次打开同一 Action 容易把历史散落到多个对话 | Action 关联稳定对话，状态改变后继续复用 |
| 排队任务容易看起来像一直在运行 | 分开显示排队、执行器领取、报告保存和送达，并暴露失败与重试 |
| 模型生成的修改建议不适合作为可靠编辑入口 | 停用可执行聊天卡片，改用校验过的管理表单 |
| 手机未连私有网络时，通知预览仍可能泄露内容 | 只推送固定通用文字，详情在 Atlas 内打开 |
| 服务商或程序版本失效 | 保留已保存请求，分类失败原因，明确备用执行策略 |

## 架构与数据归属

```mermaid
flowchart TD
    UI["浏览器 / 手机 PWA / 求职入口"] --> API["Fastify 应用"]
    API <--> DB[("PostgreSQL 规范记录")]
    Sources["只读来源与白名单文本"] --> API
    API --> Queue["持久任务与限定快照"]
    Queue --> Text["Codex：回答与求职文案"]
    Queue --> Radar["OpenClaw：迁移期间的研究"]
    Queue --> Career["Career Ops 浏览器与文档适配"]
    Text --> Check["结果与依据校验"]
    Radar --> Check
    Career --> Check
    Check --> DB
    UI --> Edits["用户提交的校验后修改"]
    Edits --> DB
    DB --> Delivery["已存报告与送达状态"]
    Delivery --> Notify["通用推送预览 / 已配置的 Discord 配送"]
```

应用和 PostgreSQL 运行在两个容器中，主机执行器和本机恢复控制器是独立进程。
手机、求职入口和主界面使用同一后台。本机使用不依赖 Tailscale，
配置中的私有远程访问才需要它。

导入行保留为来源证据。修正、归档标记和 Calendar 删除标记保留用户确认的意图。
检索采用 PostgreSQL 文本分块和词项排序，当前实现不包含独立向量数据库或 embedding 流水线。

录用结果、效率收益或完整来源覆盖。
